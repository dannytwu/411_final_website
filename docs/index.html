Controls

Game Controls

  • Player 1:
  • WASD - Movement
  • Q/E - Rotate
  • Space - Shoot
  • Player 2:
  • Arrow Keys - Movement
  • / and Right Shift - Rotate
  • . - Shoot

Tile Editor Controls

  • Mouse Click - Interact with selected tool
  • 1-5 - Select tools:
  • 1. Place tile
  • 2. Destroy tile
  • 3. Fill area
  • 4. Select fill
  • 5. Place sprite
  • Space - Test play map (requires one of each character)
  • S - Save map
  • L - Load most recent map

Post-Mortem

The final list of grievances for this project is quite long so we will try to explain them as best as possible. To begin, a major functionality of the engine, which was meant to be the coolest part, was never implemented. The ability to select which script (or game) is run on a specific map was intended to exist. For example, when making a map in the editor, pressing space would open a menu of available options from the directory, and choosing an option would attempt to load the map under that game (assuming the map met the conditions for the game). In the end, this ended up being way too difficult of a feature to implement in the time period due to both having to create a new game to test, and creating a window to select the options. Additionally, this would require a lot of change in the app.d file, which has certain aspects hardcoded to run the shootout.d file. Honestly, this would be very doable given an extra week or so, but we digress.

Furthermore, the ability to import sprites using the game engine editor itself was never added. Any sprites the user would want to add or use would have to be added to app.d itself. This feature would also be very approachable, it would've just taken time we didn't have to create the UI, link everything, check the assets folder, and potentially redo the resource manager and spritesheet. The other issue potentially would've been that adding more sprites and tile types might conflict with the nature of the engine, which is that you can create a tileset which can be used for many different games. The more sprites you add, the more hardcoded checks you'd have to make to see if a map is compatible with a certain game. For example, if a map contains sprites or tiles which aren't accounted for in a game, it effectively fails to function in that game. we don't believe there's any good solution to this, as that hardcode needs to be handled on the game side, not the engine side, so effectively is not a problem of the engine. Perhaps if we had more time to work on this project, we would've attempted to find a more ergonomic way to go about this.

Finally, the actual implementation of gameobjects, scenes, cells, players, and projectiles are overly simple, seeing as they only serve to create shootout.d. If we had more time, we would've expanded the functionalities of these classes to account for more potential game types. Giving them more attributes would allow for greater utility of their uses, and if a game was made that had no use for a certain attribute of the gameobjects then that hopefully would just be ignored with no issue. This issue goes in hand with the game, shootout.d, itself not being very fleshed out. It's very simple and runs poorly. If we had more time we would've focused more on making the different tile types usable in shootout.d, and added more interactable sprites or items to make the game more interesting. We also would've spent more time making the game run smoothly and be more intuitive to control and play.
